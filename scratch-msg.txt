fix: make the database rebuildable from the repo again

Every UI string added after Phase 1 had been applied straight to the
remote project and never committed. The repo held 34 of 193 message
keys, so a fresh Supabase project checked out from here would have come
up with the full schema and almost no strings, rendering
action.evacuate_now at people during a storm.

0012_translations_complete.sql closes it: 577 rows, 193 keys, three
languages, generated by npm run db:dump-translations and idempotent, so
it reconciles with the subset earlier migrations already insert rather
than conflicting.

The deliberate Cebuano gap survived and was checked for:
action.stay_inside and headline.stay_inside still carry only en and tl.
That absence is what gives the FR-3.5 fallback path data that exercises
it; three languages there would mean it was filled in by accident.

Only translations were missing. The one schema fix that existed remotely
without a local file is already carried by 0006 (grant execute on
private.recent_rescue_count), verified against pg_proc. The remaining
remote-only migrations are test scaffolding: row cleanups, temporary
signal changes, role grants keyed to device uids. Those must not be
replayed on a fresh database and are deliberately not reconstructed.

check:i18n now fails the build when a key the app asks for is seeded by
no migration, and it runs in verify. Dynamic key sites are declared with
the values they can take; an undeclared one fails rather than passing
silently. Verified by planting a key: the check named it and exited 1.

Caveat, documented and not fixed: these files reproduce a FRESH project.
They will not db push against the existing one, whose history was written
through MCP apply_migration under different names. Reconciling that means
rewriting the remote migration ledger, which is riskier than the problem.
